Retrieval: The system found the correct information for Q1–Q4. Q2 and Q3 required facts from two different documents, and both supporting facts appeared in the top three retrieved chunks. Q4 was an ambiguous question, but the system successfully retrieved information about both HW4 and HW3 sessions. For Q5, the system found related latency information, but none of the retrieved chunks contained the requested p99 value. For Q6, the question was unrelated to the documents, so the retrieval scores were low.

What helped: The value of k had the biggest effect on the results. When k=1, the system retrieved only one chunk, so Q2 and Q3 were incomplete because each question required information from two sources. When k=3, the system retrieved enough information to answer both questions correctly. Increasing the value to k=5 did not improve the answers. Instead, it added less relevant chunks, made the prompt longer, and gave the model more information to process. Therefore, k=3 provided the best balance between completeness and relevance.

The chunk size also helped. Using chunks of 500 characters with a 50-character overlap kept related facts together and reduced the chance of splitting important information between chunks. Removing chunks with scores below 0.55 also helped the system reject Q6 because no sufficiently relevant evidence remained.

Hallucinations: Basic RAG incorrectly answered Q6 with "Paris." It also treated the median latency value as the p99 value in Q5, even though the documents never provided a p99 measurement. The no-RAG setup performed worse because it had no documents to guide the model. It gave an invented Express.js answer for Q3 and also answered the unrelated Q6 question. Context RAG correctly refused to answer both Q5 and Q6 because the documents did not contain enough evidence.

What did not help: Prompt-based grounding rules alone were not enough to prevent the Q5 mistake. A stricter second version of the rules and an additional language-model check also failed. The local Qwen3:8B model saw a related latency number and assumed it answered the question. The problem was fixed only after adding a simple Python validation check. This check looks for the specific metric mentioned in the question. If the question asks for p99 but the retrieved text does not contain p99 information, the system refuses to answer.

How the three parts work together: Retrieval makes sure the necessary evidence is available. Context engineering removes distractions and organizes the evidence clearly. Prompt rules guide the model to stay within the documents. However, code-based checks provide an additional safety layer when the model misunderstands related information. The strongest results came from combining good retrieval, clean context, clear instructions, and automatic validation.

Limitations: Only six questions were tested, and the answers were evaluated manually. Therefore, the results show a clear pattern but cannot be treated as a statistically conclusive evaluation. Q4 also revealed a remaining weakness: although the system provided both durations, it did not clearly explain which duration belonged to HW3 and which belonged to HW4.
